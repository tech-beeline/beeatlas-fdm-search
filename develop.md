# Разработка: flow feature → main

Версия сервиса определяется по git-тегам, а теги создаёт CI только при мерже в `main`.
Поэтому корректность версии напрямую зависит от того, как вы ветвитесь и мержите.

## Flow

1. Старт от свежего `main`:

   ```sh
   git checkout main
   git pull --ff-only
   git checkout -b feature/<TASK>
   ```

2. Разработка — обычные коммиты (`feat:`, `fix:`).

3. Push и MR в `main`. Пайплайн `feature-build` соберёт версию вида `<next>-dev.<N>.g<sha>`.

4. Держите ветку свежей — периодически и обязательно перед мержем вливайте `main`:

   ```sh
   git checkout main && git pull --ff-only
   git checkout feature/<TASK>
   git merge main
   git push
   ```

   Так релизные теги остаются достижимыми, а версия — корректной.

5. Merge request → `main` (только через MR, без прямого push и force-push).

6. CI на мерже ставит релизный тег (`bump-version`) и запускает `release-build` с точной версией.

7. После мержа удалите feature-ветку и обновите локальный `main`.

## Запрещено

- ветвиться не от `main` (или от устаревшего коммита);
- `force-push`/`rebase` по `main` и релизным тегам;
- пушить в `main` напрямую (только MR).

## Почему версия может «слетать»

- **Ветка не содержит свежих тегов.** `git describe` видит только теги-предки `HEAD`.
  Если ветка ответвлена от старого коммита и в неё долго не вливали `main`, релизные
  теги, появившиеся в `main` позже, для неё недостижимы — ближайший тег остаётся старым.
- **Ветка далеко от тега + shallow-клон.** CI клонирует репозиторий shallow (`GIT_DEPTH`).
  Если ближайший тег за пределами загруженной истории, `git describe` не срабатывает и
  версия уходит в fallback. `.vars` углубляет историю (`git fetch --deepen`), но лучше
  не доводить до этого.
- **Ветвление не от `main`.** База от другой feature-ветки или старого коммита переносит
  в новую ветку устаревшую историю и старые теги.
- **Переписывание истории.** `rebase`/`force-push`/squash по `main` или базовой ветке
  отрывает теги от истории — `git describe` перестаёт их находить.
- **Ручные теги.** Тег, поставленный вручную на feature/develop, становится «ближайшим»
  и даёт некорректную версию. Теги ставит только CI при релизе.
- **Прямой push в `main`.** `bump-version` запускается только на merge-коммитах;
  прямой push в `main` пропускает бамп → новый тег не появляется.
